# Архитектура доставки результатов анализов в мобильное приложение

## Текстовое описание решения
Предлагается перейти от ненадёжной цепочки с прямой передачей данных к событийному потоку через брокер сообщений. Параллельно передавать событие о готовности результата в сервис уведомлений, который отправит его пациенту.

Основания для изменения: 
- Сейчас FTP падает с 425, восстановление выполняется вручную, задержка достигает двух часов
- При восстановлении создаются дубли и возникают ситуации, когда LIS передала данные, но CRM не обновилась. 
- Существующий RabbitMQ также уже перегружается в пики и приводит к потере уведомлений.

Рекомендуется подход Event-Driven Architecture + Pub/Sub с гарантией at-least-once + идемпотентность на стороне потребителя. Kafka дополнительно даёт долговременное хранение, возможность повтора и горизонтальное масштабирование обработки через партиции. Таким образом, основная цепочка становится асинхронной, слабосвязанной и масштабируемой, а пользовательское чтение остаётся синхронным и быстрым. Это сочетает гарантированную доставку с минимальной задержкой появления результата в мобильном приложении.

## Сравнение вариантов

| Вариант | Гарантированная доставка | Масштабирование / задержка | Эксплуатация | Решение |
| --- | --- | --- | --- | --- |
| Прямой REST LIS → CRM/Results Service | Низкая: сохраняется временная связанность. При недоступности получателя нужны повторы | Низкая задержка, но получатель должен быть доступен | Просто на старте, сложно восстанавливать сбои | Не рекомендуется |
| RabbitMQ | At-least-once через publisher confirms + consumer ack | Низкая задержка, можно масштабировать потребителей | Проще Kafka, но существующий RabbitMQ уже перегружается и теряет сообщения | Не рекомендуется для критичного потока |
| Kafka + at-least-once | Высокая: acks=all , коммит offset после обработки, идемпотентность по eventId | Высокая: партиционирование + consumer groups, обработка практически сразу после публикации | Сложнее RabbitMQ, но есть replay и понятный механизм восстановления | Рекомендуется |
| Kafka exactly-once | Максимальная: транзакции + идемпотентность | Высокая | Наиболее сложная реализация | Избыточно для передачи результатов анализов |

## Блок-схема потока данных

```
@startuml
title Доставка результатов анализов в мобильное приложение

participant "LIS\n(лабораторная)" as LIS
participant "Integration Service" as Integration
database "Results DB\n+ Outbox" as DB
queue "Kafka\nlab-results.events" as Kafka
participant "Results Service" as Results
participant "Уведомления" as Notifications
participant "API Gateway" as Gateway
participant "Мобильное приложение" as Mobile

== 1. Результат готов ==

LIS -> Integration : Результат анализа\nREST / JSON
Integration -> DB : Транзакция:\nсохранить результат\n+ outbox(eventId)
DB --> Integration : Commit

== 2. Гарантированная публикация ==

Integration -> Kafka : AnalysisResultReady\nacks=all
Kafka --> Integration : Ack

note right of Integration
При ошибке публикации
запись остаётся в outbox
и отправляется повторно
end note

== 3. Обработка результата ==

Results -> Kafka : Poll
Kafka --> Results : AnalysisResultReady
Results -> Results : Проверить eventId

alt Событие ещё не обработано

    Results -> DB : Сохранить / обновить результат
    Results -> Kafka : Commit offset

else Дубликат

    Results -> Kafka : Commit offset\nбез повторной записи

end

== 4. Уведомление пациента ==

Notifications -> Kafka : Poll
Kafka --> Notifications : AnalysisResultReady
Notifications --> Mobile : Push\n«Результат анализа готов»

== 5. Получение результата ==

Mobile -> Gateway : GET запрос результата анализов

Gateway -> Results : GET запрос результата анализов

Results -> DB : Получение результата анализов

DB --> Results : Результат анализов

Results --> Gateway : 200 OK

Gateway --> Mobile : 200 OK + результат
@enduml
```
