# Автоматизация бизнес-операции «Запись к врачу с оплатой и резервированием сдачи анализов»

## Успешный сценарий
В успешном сценарии единым владельцем процесса должен выступать оркестратор записей (Appointment Saga Orchestrator). Он последовательно проверяет полис, резервирует слот врача, проводит оплату, резервирует время забора биоматериала и только после успешного завершения всех критичных шагов подтверждает запись пациенту. 

#### Диаграмма последовательности
```
@startuml

title Успешный сценарий записи пациента

actor "Пациент" as Patient
participant "Мобильное приложение" as Mobile
participant "API Gateway" as Gateway
participant "Appointment Saga\nOrchestrator" as Saga
participant "1С: Полисы" as Policy
participant "Расписание" as Schedule
participant "Платёжный шлюз" as Payment
participant "LIS" as LIS

Patient -> Mobile : Выбрать врача,\nвремя и исследование
Mobile -> Gateway : POST /appointments\nIdempotency-Key
Gateway -> Saga : Создать процесс записи

== Проверка полиса ==

Saga -> Policy : Проверить полис ДМС
Policy --> Saga : Полис действителен

== Бронирование приёма ==

Saga -> Schedule : Зарезервировать слот врача\nIdempotency-Key
Schedule --> Saga : Слот зарезервирован

== Оплата ==

Saga -> Payment : Провести оплату\nIdempotency-Key
Payment --> Saga : Оплата успешна

== Бронирование лаборатории ==

Saga -> LIS : Зарезервировать время\nзабора биоматериала\nIdempotency-Key
LIS --> Saga : Слот лаборатории зарезервирован

== Завершение Saga ==

Saga -> Schedule : Подтвердить запись
Schedule --> Saga : Запись подтверждена
Saga --> Gateway : SUCCESS
Gateway --> Mobile : 201 Created\nЗапись подтверждена
Mobile --> Patient : Показать подтверждение

@enduml
```

## Выбор типа Saga
Для этого процесса подходит Fairy Tale Saga: оркестрация + синхронное взаимодействие + итоговая согласованность. Процесс содержит несколько зависимых шагов, включая внешнюю оплату и legacy-системы, поэтому централизованный оркестратор упрощает контроль состояния, аудит и запуск компенсаций. Строгая атомарная транзакция между расписанием, 1С, платёжным шлюзом и LIS невозможна, поэтому система допускает временную несогласованность, но должна в итоге прийти к согласованному состоянию.

## Компенсирующие транзакции

| Шаг сценария | Компенсирующее действие | Риск, который устраняется |
| --- | --- | --- |
| Резервирование слота врача | Cнять резерв и вернуть слот в доступное расписание | Пациент не занимает слот после неуспешной оплаты или сбоя последующих шагов |
| Оплата консультации | Инициировать возврат по исходной операции | Устраняет ситуацию «деньги списаны, а запись не оформлена», которая уже происходила |
| Резервирование слота лаборатории | Отменить резерв времени забора биоматериала | Не остаются «зависшие» лабораторные слоты после отмены всей записи |

Компенсации выполняются в обратном порядке успешных шагов. Они должны быть идемпотентными, а оркестратор должен хранить состояние Saga и факт выполнения каждой компенсации. 

Проверка полиса компенсации не требует: это операция чтения, которая не изменяет бизнес-состояние.

## Идемпотентность на входе
1. Мобильное приложение генерирует уникальный Idempotency-Key для каждой попытки оформления записи и передаёт его в запросе
2. API Gateway передаёт ключ в Appointment Saga Orchestrator. 
3. Оркестратор сохраняет связь с ключом.
4. Если из-за таймаута, плохой мобильной сети или повторного нажатия приходит запрос с тем же ключом, новая Saga не создаётся. Клиент получает состояние и результат уже существующего процесса. Тот же принцип распространяется на мутирующие шаги Saga — бронирование врача, оплату и бронирование лаборатории.
