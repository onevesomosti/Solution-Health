# Стратегия горизонтального масштабирования

Для целевой нагрузки наиболее критичны системы "Расписание" и "Уведомления". Расписание обслуживает основную функцию мобильного приложения и уже испытывает блокировки PostgreSQL. RabbitMQ для уведомлений уже перегружается в пики, хотя целевая архитектура существенно увеличит объём асинхронных событий и push-уведомлений. 

| ИТ-система | Реализация горизонтального масштабирования | Ограничение | Описание решения для него |
| --- | --- | --- | --- |
| Расписание (Java + PostgreSQL) | Сделать экземпляры Java-сервиса stateless и разместить несколько экземпляров за балансировщиком. Количество экземпляров изменять через автомасштабирование. Для PostgreSQL — добавить read replicas и направить на них операции чтения доступных слотов. Запись и резервирование слота оставить на основном экземпляре. | PostgreSQL остаётся stateful-узким местом: горизонтальное масштабирование Java-сервиса само по себе не устранит существующие блокировки таблицы слотов. | Разделить потоки чтения и записи: массовые запросы мобильного приложения на просмотр расписания направлять на read replicas, а операции бронирования — на основной экземпляр. Это разгрузит систему от преобладающей нагрузки чтения |
| Уведомления (RabbitMQ) | Сервис уведомлений сделать stateless и запускать несколько экземпляров потребителей. Сообщения хранить в распределённом брокере. Увеличивать число потребителей вместе с ростом очереди. Сам RabbitMQ развернуть отказоустойчивым кластером | Брокер остаётся stateful-компонентом и требует отдельного масштабирования. Добавление потребителей не поможет, если узкое место находится в самом RabbitMQ. Сейчас пики уже создают огромные очереди и приводят к потере уведомлений | Масштабировать независимо два уровня: RabbitMQ как кластер, а потребителей горизонтально по глубине очереди. Настроить подтверждения для at-least-once, чтобы сообщение удалялось только после подтверждения обработки.|
