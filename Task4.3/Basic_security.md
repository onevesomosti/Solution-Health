# Проектирование базовых мер безопасности

## Аутентификация мобильного приложения

Для пациентов предлагается использовать OIDC поверх OAuth2 с централизованным Identity Provider (IdP). OIDC отвечает за идентификацию пользователя, а после успешной аутентификации приложение получает короткоживущий JWT access token с идентификатором пользователя и его правами. Такой stateless-подход не требует общей серверной сессии и лучше подходит для горизонтально масштабируемого мобильного контура.

#### Схема аутентификации
```
@startuml

title Аутентификация пациента в мобильном приложении

actor "Пациент" as Patient
participant "Мобильное приложение" as Mobile
participant "Identity Provider\n(IdP)" as IdP
participant "API Gateway" as Gateway
participant "Внутренний сервис" as Service


Patient -> Mobile : Войти в приложение
Mobile -> IdP : Аутентификация пользователя\nOIDC / OAuth2
IdP --> Mobile : Access Token\nJWT + scope
Mobile -> Gateway : HTTPS / REST\nAuthorization: Bearer JWT
Gateway -> Gateway : Проверка подписи,\nсрока действия и scope

alt Токен корректен
    Gateway -> Service : Запрос пользователя
    Service --> Gateway : Ответ
    Gateway --> Mobile : 200 / 201
else Токен недействителен
    Gateway --> Mobile : 401 Unauthorized
end

@enduml
```

## Rate Limiting

Rate limiting следует централизованно применять на API Gateway, а не реализовывать независимо в отдельных сервисах. Для мобильного приложения подходит Token Bucket, он допускает кратковременные пользовательские всплески, сохраняя ограничение средней нагрузки.

| Тип запроса | Лимит | Действие при превышении |
| --- | --- | --- |
| Публичный поиск врачей | 50 запросов/мин на IP, Token Bucket | API Gateway прекращает пропуск запросов и возвращает 429 Too Many Requests. Клиент повторяет запрос после задержки |
| Авторизованное создание записи | 200 запросов/мин на пользователя, идентификация по sub или user_id из JWT, Token Bucket | Gateway возвращает 429 Too Many Requests. Счётчик ведётся отдельно для каждого пользователя, повтор выполняется с backoff |

Для горизонтально масштабируемого API Gateway счётчики необходимо хранить централизованно, например в Redis, чтобы лимит оставался единым для всех экземпляров шлюза. Для создания записи rate limiting должен использоваться вместе с Idempotency-Key, ограничение частоты защищает от перегрузки но само по себе не предотвращает двойную запись при повторном запросе. 

## Меры защиты каналов передачи данных
1. Мобильное приложение > API Gateway — только HTTPS/TLS. Медицинские, персональные данные и JWT не должны передаваться по незашифрованному каналу.
2. API Gateway > внутренние критичные сервисы — mTLS. Обе стороны предъявляют сертификаты, поэтому канал одновременно шифруется и подтверждается подлинность вызывающего сервиса.
3. Централизованное управление сертификатами - через Vault или cert-manager, короткоживущие сертификаты и автоматическая ротация до истечения срока.
4. WAF перед API Gateway для блокировки SQL Injection и XSS. Это особенно важно, поскольку инциденты уже подтверждают SQL-инъекцию в веб-портале.
5. CDN/DDoS Protection > WAF > API Gateway > сервисы как эшелонированная защита публичного периметра. Rate limiting на одном Gateway недостаточен против распределённой атаки.
6. JWT проверяется только подпись, срок действия и права (scope). Сам JWT не должен содержать медицинские данные или другие секреты.

Таким образом, безопасность строится эшелонированно: 
- TLS защищает внешний канал, 
- OIDC/JWT — идентификацию и права пациента, 
- API Gateway — аутентификацию и rate limiting, 
- WAF/CDN — периметр, 
- mTLS — внутренние взаимодействия.
