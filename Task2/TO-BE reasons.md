## Особенности новой архитектуры
- синхронные запросы остаются там, где пациенту нужен немедленный результат: слоты, создание записи, оплата, чтение результатов, проверка полиса.
- асинхронный Event-Driven, Pub/Sub используется для фактов, которые уже произошли: создание или изменение записи, поступление результатов, отправка уведомлений.
- API Gateway изолирует внешний мобильный канал и централизует управление.
- Anti-Corruption Layer изолирует новые API от нестабильных контрактов 1С и LIS.
- Новые компоненты должны проектироваться stateless, поскольку целевое состояние требует горизонтального масштабирования

## Обоснование новых интеграций

| Интеграция | Стиль / паттерн | Почему |
| --- | --- | --- |
| Мобильное приложение → API Gateway | Синхронный REST + External API Gateway | Мобильное приложение — внешний клиент. Gateway даёт единую точку входа для маршрутизации, аутентификации, rate limiting и идемпотентности. В INT-010 прямо требует API Gateway с rate limiting и идемпотентностью |
| Мобильное приложение → Identity Provider | OIDC/OAuth2 + JWT, stateless | OIDC отвечает за идентификацию пользователя, OAuth2 — за определение доступа. Токен позволяет не хранить серверную сессию и соответствует stateless-подходу |
| API Gateway → Расписание | Синхронный REST + Idempotency-Key| Пользователю нужен немедленный результат при выборе слота и записи. При этом в INT-005 указано что появляются дубли при повторных POST |
| API Gateway → Платёжный шлюз | Синхронный REST + Idempotency-Key + Timeout, Retry,Circuit Breaker, Fallback | Результат оплаты критичен и нужен пользователю немедленно, но в INT-001 указано неопределённое состояние при таймауте. Для критичных внешних вызовов рекомендуется цепочка Timeout → Retry → Circuit Breaker → Fallback, причём retry допустим только для идемпотентной операции |
| API Gateway → Integration Layer → 1С | Синхронный API + Anti-Corruption Layer + Circuit Breaker | Проверка ДМС требует ответа в пользовательском сценарии, но 1С нестабильна. ACL изолирует мобильный контракт от формата legacy-системы; Gateway не должен сам выполнять трансформацию данных |
| LIS → Integration Layer → Event Broker → CRM | Гибрид: адаптер + асинхронный Pub/Sub, eventual consistency | Результат анализа не требует синхронного ответа пациенту. Сейчас поток имеет задержки, ручное восстановление и дубли. Асинхронность устраняет временную связанность, а брокер буферизует сообщения при недоступности CRM |
| Расписание → Event Broker → Уведомления | Event-driven, Pub/Sub | Подтверждение записи уже произошло, отправка push не должна блокировать запись. Pub/Sub подходит, когда свершившийся бизнес-факт вызывает независимые реакции, а сбой консьюмера не должен останавливать основной процесс |
| Integration Layer → Event Broker → Уведомления | Event-driven, Pub/Sub | После получения результата анализа формируется событие, уведомление становится независимой фоновой реакцией. Это отделяет доступность внутренней системы от доступности провайдера|
