# Выявленные системные проблемы и риски

| Проблема | Признаки | Влияние на приложение |
| --- | --- | --- |
| Отсутствие идемпотентности | - Дубли записей при повторных POST запросах (INT-005, SD-003) | Повторное нажатие или retry может создать дубли записей |
| Ненадёжный платёжный поток | - При таймауте деньги списываются, но статус платежа не фиксируется (INT-001). <br>- Происходят двойные списания (отзывы сотрудников).| Пользователь может получить ошибку при фактически списанных деньгах либо заплатить дважды. Это блокирующий риск для MVP, где оплата это базовая функция |
| Синхронная зависимость от нестабильной 1С | - Проверка полиса выполняется через HTTP, 1С отвечает 503 при нагрузке >50 rps (INT-003).<br> - Иногда ответ занимает более 30 секунд, контракт меняется без уведомлений (отзывы сотрудников) | Управление ДМС становится временно связано с доступностью legacy-системы. Рост мобильного трафика способен увеличить количество 503 и зависаний. Синхронные зависимости без защитных механизмов создают риск каскадных отказов |
| Расписание уже является узким местом | - В часы пик возникают блокировки на таблице слотов, изменения врачей задерживаются или не фиксируются (отзывы сотрудников). <br> - Требуется репликация для чтения (INT-009) | Просмотр слотов и запись (основной сценарий приложения) может деградировать первым при росте нагрузки. Требование дальнейшего роста до 50 000 пользователей становится недостижимым без устранения этого узкого места|
| RabbitMQ не выдерживает текущие пики | - На пиках возникают большие очереди, превышение лимита уже приводило к ошибке 404 и потере уведомлений (отзывы сотрудников). <br> - Лимиты RabbitMQ даже не документированы (INT-004) | Push-уведомления — функция MVP. Пользователь может не получить подтверждение записи или другое критичное уведомление. Рост мобильной аудитории дополнительно увеличит поток сообщений |
| Ненадёжный поток LIS → CRM | - FTP-загрузка падает с 425 и требует ручного восстановления (INT-002)<br> - Отсутствуют автоматические повторы, задержка данных до двух часов, старый Perl-коннектор не сопровождается и не документирован (отзывы сотрудников).<br> - Есть дубли анализов (INT-008) и неактуальные данные в CRM (INT-011)| Приложение не сможет гарантировать своевременное и корректное отображение результатов анализов: возможны задержки, пропуски и дубли |
| Нет централизованной точки входа для мобильного клиента | - В AS-IS входной точкой является веб-портал, API Gateway отсутствует. <br> - В INT-010 требуется разработать Gateway с rate limiting и идемпотентностью | Без Gateway сложнее централизованно обеспечить маршрутизацию, rate limiting, аутентификацию, завершение TLS-соединения и наблюдаемость внешнего мобильного трафика. Эти функции относятся к стандартной ответственности внешнего API Gateway |
| Нестабильные и недокументированные API-контракты | - 1С без уведомления изменила ответ с JSON на XML  <br> - LIS-коннектор не документирован (отзывы сотрудников)| Изменение системы может неожиданно сломать приложение или его интеграционный слой. Для мобильных клиентов риск особенно высок, поскольку старые версии приложения продолжают использовать API. Необходимы явные контракты и управление их изменениями |
| Недостаточная наблюдаемость интеграций | - Отсутствует distributed tracing, сложно найти корень сбоя (INT-007)| При цепочке Mobile → backend → расписание/платёж/CRM/1С определить источник роста задержек или ошибок будет сложно. Это увеличивает время восстановления и угрожает целевой доступности P99,P95 |
| Архитектура не готова к целевому горизонтальному масштабированию | - Уже при текущей нагрузке наблюдаются блокировки БД расписания, перегрузка RabbitMQ и отказ 1С при >50 rps (INT-003, отзывы сотрудников) | Даже если само мобильное backend-приложение масштабировать горизонтально, зависимые компоненты останутся узкими местами. Горизонтальное масштабирование должно охватывать всю критическую цепочку, а не только новый мобильный контур |
| Не определён контур аутентификации и авторизации мобильного приложения | - В AS-IS описан HTTPS-доступ через веб-портал, но отдельного механизма идентификации и авторизации мобильного пользователя в архитектуре нет.| Приложение предоставляет доступ к персональным данным, результатам анализов, полисам и оплате. До внешнего запуска необходимо явно определить кто обращается к API и что ему разрешено делать  |
