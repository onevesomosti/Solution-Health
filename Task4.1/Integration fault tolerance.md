# Реализация отказоустойчивости интеграции между ИТ-системами

## Параметры отказоустойчивости 1C и платежного шлюза

В обоих случаях используется цепочка Timeout > Retry > Circuit Breaker > Fallback. При этом Retry допустим только для идемпотентных операций. Для платежей это особенно важно из-за уже зафиксированных двойных списаний.

| ИТ-система | Timeout | Retry | Fallback |
| --- | --- | --- | --- |
| 1С: Полисы | 1 с.  | 1 повтор, экспоненциальная задержка 200 мс + jitter (предотвращает одновременные повторные обращения множества клиентов) | Сначала вернуть последнее актуальное значение из кэша. Если его нет, то применить Fail Fast и сообщить что проверка полиса временно недоступна |
| Платёжный шлюз (критичный) | 1,2 с. | 2 попытки, exponential backoff 200/400 мс, только с Idempotency-Key | Вернуть «Платёж в обработке», сохранить операцию в PENDING. Оотдельно проверить окончательный статус и при необходимости запустить компенсацию |

## Приоритет Circuit Breaker

Circuit Breaker приоритетнее внедрить для 1С по причине подтверждённой систематической деградации под нагрузкой. Без Circuit Breaker новые запросы и Retry продолжают нагружать уже деградировавшую 1С, что создаёт условия для каскадного отказа мобильного сценария записи.

Предлагаемые параметры:
- failureRateThreshold = 30%
- slidingWindowSize = 20
- slidingWindowType = COUNT_BASED
- waitDurationInOpenState = 30 s
- permittedNumberOfCallsInHalfOpen = 3
- slowCallDurationThreshold = 1 s

Механизм работает в трёх состояниях:
CLOSED > OPEN > HALF-OPEN > CLOSED.

В CLOSED вызовы проходят в 1С. Если в окне из 20 вызовов доля ошибок превышает 30%, Circuit Breaker переходит в OPEN и 30 секунд вообще не вызывает 1С, сразу переходя к fallback. Затем в HALF-OPEN пропускаются только три тестовых запроса: если они успешны — поток восстанавливается, если нет — Circuit Breaker снова переходит в OPEN.Такой механизм предотвращает постоянную нагрузку на ещё не восстановившийся сервис.

Для платёжного шлюза Circuit Breaker также нужен, но там основная опасность — неопределённый результат операции: деньги могли быть списаны до таймаута. Поэтому кроме CB критичны Idempotency-Key, фиксация PENDING и отдельная проверка статуса платежа. 

## Снижение нагрузки на 1С

Предлагается поставить перед legacy-системой отдельный Anti-Corruption Layer с кэшем результатов проверки полисов. 

Повторные чтения сначала обслуживаются из кэша. Только при отсутствии актуального значения Policy Service обращается к 1С. Дополнительно исходящий поток к 1С ограничивается rate limiting, чтобы мобильное приложение не передавало всплеск нагрузки непосредственно в legacy-систему. Это особенно важно, поскольку сейчас rate limiting отсутствует и 1С перестаёт отвечать при небольшом всплеске.

Это позволяет изолировать наиболее проблемную legacy-зависимость от роста мобильного канала.

#### Диаграмма C4 Level 1

```
@startuml

!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Context.puml

LAYOUT_TOP_DOWN()

title Проверка полиса ДМС — снижение нагрузки на 1С


' ====================== Пользователь ======================

Person(patient, "Пациент", "Записывается на прием")


' ====================== Клиент ======================

System(mobileApp, "Мобильное приложение", "Запись, оплата, полисы ДМС, результаты анализов, уведомления")


' ====================== Интеграционный слой ======================

System(apiGateway, "API Gateway", "Единая внешняя точка входа: маршрутизация, JWT, rate limiting, Idempotency-Key")

System(policyService, "Policy Service", "Anti-Corruption Layer, кэширование и защита интеграции с 1С")

System(policyCache, "Policy Cache", "Кэш результатов проверки полисов")


' ====================== Существующая система ======================

System(policySystem, "1С: Полисы", "HTTP-шлюз")


' ====================== Связи ======================

Rel(patient, mobileApp, "Проверяет полис при записи", "HTTPS")

Rel(mobileApp, apiGateway, "Проверка полиса", "HTTPS / REST + JWT")

Rel(apiGateway, policyService, "Проверить полис", "REST")

Rel(policyService, policyCache, "Получить последнее актуальное состояние", "Cache")

Rel(policyService, policySystem, "Проверка при cache miss", "HTTP / Timeout + Retry + Circuit Breaker")


' ====================== Примечание ======================

note right of policyService
Основной поток:
1. Проверить кэш
2. Cache hit → вернуть результат
3. Cache miss → вызвать 1С
4. Ограничить поток запросов к 1С
5. При сбое → Circuit Breaker + fallback
end note

@enduml
```
